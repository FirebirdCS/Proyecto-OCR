01

Propósito y alcance

La Plataforma OCR es un sistema de incentivos de venta. Los participantes suben fotos o PDF de sus comprobantes de compra, el sistema extrae el texto con OCR, reconoce los productos de una campaña y acredita puntos que llevan a hitos con recompensas.

Este manual está dirigido a quien desarrolla, despliega u opera la plataforma. Describe el estado del código en la rama master del repositorio FirebirdCS/Proyecto-OCR a octubre de 2026.

Convenciones

  • Los comandos se ejecutan desde la raíz del repositorio, salvo que se indique otra carpeta.
  • Los comandos de PowerShell aparecen con rutas de Windows (.\scripts\…); los de pnpm funcionan igual en cualquier sistema.
  • Los nombres de archivos, variables y rutas de la API se escriben en monoespaciado.

02

Arquitectura

Cliente-servidor con servicios administrados de Google. El sitio web es estático; toda escritura de datos pasa por la API, que es la única con privilegios sobre Firebase.

Capas del servidor

CapaCarpetaResponsabilidad
Rutasserver/src/routesAutenticar, validar la entrada con Zod, llamar a un servicio y responder. No acceden a Firestore.
Middlewareserver/src/middlewarerequireAuth, requireAdmin, requireRole y el manejador central de errores.
Serviciosserver/src/servicesReglas de negocio y todo el acceso a Firebase, Vision y correo.
Tipos y esquemasserver/src/typesTipos del dominio junto a sus esquemas Zod. El cliente tiene un espejo en client/src/types.
Utilidadesserver/src/utilsFunciones puras: comparación de productos, revisión de comprobantes, calendario, HttpError.

Flujo de una petición

  1. El cliente obtiene el token de ID de Firebase (auth.currentUser.getIdToken()) y lo envía en Authorization: Bearer ….
  2. requireAuth verifica el token con el Admin SDK y deja en req.user el uid y el rol del claim.
  3. La ruta valida el cuerpo con Zod; un error de validación se convierte en 400.
  4. El servicio aplica las reglas y escribe en Firestore, casi siempre dentro de una transacción.
  5. Cualquier HttpError llega a errorHandler, el único lugar que da forma a las respuestas de error.

Instalación local

Requisitos

  • Node.js 22.13 o superior (.nvmrc fija la versión 22) y pnpm 11.15.1.
  • Acceso al proyecto de Firebase proyecto-ocr-d3ecd, con la API de Cloud Vision habilitada.
  • Una llave de cuenta de servicio del Admin SDK guardada como server/serviceAccount.json (Firebase Console → Configuración del proyecto → Cuentas de servicio → Generar nueva clave privada).
  • Python 3 y Microsoft Edge, solo para generar los comprobantes de prueba.

Pasos

  1. Instala dependencias: pnpm install.
  2. Copia server/.env.example a server/.env y client/.env.example a client/.env. Completa los valores (capítulo 6).
  3. Inicia ambos paquetes: pnpm dev. El sitio queda en http://localhost:5173 y la API en http://localhost:4000.
  4. Crea el primer administrador: pnpm user:create correo@empresa.com admin "Nombre". El comando imprime el enlace para elegir contraseña.
  5. Genera comprobantes de prueba: python samples\generate_samples.py (agrega --limites para los de valores límite).
Errores de proxy al arrancar

Vite suele estar listo antes que la API. Las primeras peticiones pueden registrar http proxy error … ECONNREFUSED; desaparecen al recargar la página una vez que aparece API listening on http://localhost:4000.

07

Autenticación y roles

Hay dos roles, admin y user. La fuente de verdad es el custom claim role del token de Firebase.

El rol también se copia en users/{uid}, pero solo para listar y buscar cuentas. Ninguna decisión de autorización lee esa copia. El mismo claim se aplica en tres lugares sin consultas adicionales:

  1. La API, con requireAuth, que decodifica el token.
  2. Las reglas de Firestore, con request.auth.token.role.
  3. El cliente, con el token decodificado en AuthContext, que decide el menú y las rutas.

Reglas

  • Sin registro público. Las cuentas las crea un administrador (POST /api/admin/users) o la terminal (pnpm user:create). Se asigna una contraseña aleatoria que nadie ve y se envía un enlace de restablecimiento; nunca se envía una contraseña.
  • Mensaje de acceso genérico. El inicio de sesión responde igual a un correo inexistente que a una contraseña incorrecta, para no revelar qué cuentas existen.
  • Propagación. Un cambio de rol tarda hasta una hora en llegar al token. El cliente fuerza la renovación con refreshRole() cuando /api/me devuelve un rol distinto.
  • Protección contra bloqueo. Un administrador no puede quitarse su rol ni deshabilitarse. BOOTSTRAP_ADMIN_EMAILS devuelve el rol de administrador a esos correos al iniciar sesión.
  • Solo el rol user escanea. POST /api/ocr usa requireRole('user'); un administrador no puede acreditarse puntos.

Cloud Storage

Cada archivo escaneado, con o sin puntos, se guarda en receipts/{uid}/{documentId}.{ext} del bucket proyecto-ocr-d3ecd.firebasestorage.app. storage.rules niega todo acceso desde el navegador; los administradores ven los archivos con URL firmadas de 10 minutos.

10

Procesamiento de comprobantes

POST /api/ocr recorre estos pasos. Los primeros se ejecutan antes de llamar a Vision, así que un escaneo rechazado ahí no tiene costo.

  1. Rol y archivo. Solo el rol user; Multer acepta PNG, JPEG, WebP, TIFF y PDF hasta OCR_MAX_UPLOAD_MB.
  2. Campaña. assertCanScan: el usuario debe participar (403) y la campaña debe estar activa y con startsAt ≤ ahora < endsAt (409).
  3. Límite diario. Cuenta todos los escaneos de 24 horas móviles; al llegar a SCAN_DAILY_LIMIT responde 429. Si falta el índice, el límite se omite y se registra un error.
  4. Archivo repetido. Si el hash SHA-256 del archivo ya tiene guarda, 409 sin llamar a Vision.
  5. OCR. Vision devuelve palabras con su geometría. rebuildLines endereza la página según el ángulo medio de las palabras y reconstruye los renglones, porque Vision separa las columnas del ticket y alejaría cada precio de su producto. De un PDF se leen las primeras 5 páginas.
  6. Revisión del comprobante (receiptChecks.ts): debe tener una línea TOTAL con importe (en la línea o en las dos siguientes) y una fecha dentro de [inicio de la campaña, min(fin, hoy)], en STATS_TIME_ZONE. Si falla, 0 puntos.
  7. Productos (receiptMatching.ts): solo los de la campaña elegida y activos. Ignora espacios, puntuación y acentos; tolera un error en nombres de 5+ letras (dos en 12+); las cifras deben coincidir exactamente; el SKU se compara exacto; si varios coinciden, gana el más largo. Una línea sin importe no cuenta.
  8. Cantidades. Reconoce «2 x 15.00», «x2», «3 un», «cant: 2» o un número al inicio. Ante la duda cuenta 1 unidad: dar de menos es el fallo elegido. El total se recorta a RECEIPT_MAX_UNITS.
  9. Transacción. En una sola transacción se escriben el documento, el avance del participante (puntos = unidades × puntos de la campaña, hito, requisitos), las guardas y los totales de salesDaily. El archivo se sube antes y se borra si la transacción falla.

Guardas contra duplicados

Solo se escriben para comprobantes que acreditaron puntos, así que uno rechazado puede volver a enviarse con una foto mejor.

  • file-<sha>: el mismo archivo.
  • text-<sha>: el mismo texto normalizado.
  • receipt-<sha>: fecha, total y número de ticket (o la hora, o los productos y cantidades). Detecta una foto nueva del mismo papel, desde cualquier cuenta. Si el OCR lee mal un dígito, la guarda falla y queda la revisión manual.

Marcas de revisión

No cambian los puntos; envían el comprobante al filtro «Para revisar»: units_capped, large_line_quantity (10 o más unidades en una línea), frequent_scanner (cinco escaneos previos en 24 horas) y file_not_stored.

Anulación

POST /admin/scans/:id/void resta los puntos, unidades, hito y requisitos del participante y los totales de salesDaily del día del escaneo, y registra quién anuló, cuándo y por qué. Las guardas se conservan: un comprobante anulado no puede volver a subirse.

11

Panel de indicadores

Cada comprobante acreditado incrementa el documento salesDaily/{día}, con el día cortado en STATS_TIME_ZONE. GET /api/admin/dashboard lee como máximo unos 365 de esos documentos y arma tres series: 30 días, 12 semanas (desde el lunes) y 12 meses, más los productos más vendidos de cada periodo. Nunca recorre documents.

Límite de escritura

Todos los escaneos de un día escriben el mismo documento, lo que limita el ritmo sostenido a cerca de un comprobante acreditado por segundo. Si el volumen crece, hay que repartir el contador en varios documentos.

12

Seguridad

Controles

  • Secretos fuera del repositorio. server/serviceAccount.json y server/.env están en .gitignore. La configuración web de Firebase (client/.env) es pública por diseño.
  • Sin llave en producción. En Cloud Run la API corre como la cuenta de servicio del Admin SDK y obtiene credenciales del entorno. GOOGLE_APPLICATION_CREDENTIALS y VISION_KEY_FILE deben quedar sin definir allí.
  • Escrituras solo por la API. Reglas de Firestore y Storage niegan toda escritura desde el navegador.
  • Cabeceras y CORS. Helmet en todas las respuestas; CORS limitado a CLIENT_ORIGIN.
  • Validación en el servidor. Las reglas de campaña (fechas, productos repetidos, hitos ascendentes, mínimos, productos activos) viven en campaignInputSchema; el formulario solo las refleja.
  • Evidencia privada. Archivos solo accesibles con URL firmadas de 10 minutos.
  • Clave de Resend en Secret Manager (resend-api-key), cargada con scripts\set-resend-key.ps1, que la pide sin mostrarla.

Despliegue

API en Cloud Run

Servicio ocr-api, región us-central1, cuenta firebase-adminsdk-fbsvc@proyecto-ocr-d3ecd.iam.gserviceaccount.com. Con la CLI de Google Cloud instalada y gcloud auth login hecho:

.\scripts\deploy-api.ps1 -SkipSetup `
  -ClientOrigins http://localhost:5173,https://ganevel.corvelsa.com `
  -ClientAppUrl https://ganevel.corvelsa.com
  • Construye la imagen desde el Dockerfile (node:22-slim, pnpm 11.15.1, solo dependencias de producción) y despliega con 1 GiB de memoria, 120 s de tiempo máximo y hasta 3 instancias.
  • Sin -SkipSetup (primera vez) habilita Cloud Run, Cloud Build y Artifact Registry, y concede a la cuenta roles/iam.serviceAccountTokenCreator sobre sí misma. Sin ese permiso las URL firmadas de la evidencia fallan con 500.
  • Parámetros: -TimeZone, -ScanDailyLimit, -ReceiptMaxUnits, -BootstrapAdminEmails, -AppName, -ResendFrom. La URL resultante queda en scripts\.last-deploy-url.txt.

Sitio en GitHub Pages

.github/workflows/pages.yml publica el sitio en cada envío a master. Requiere:

  • Settings → Pages → Source: GitHub Actions.
  • Settings → Secrets and variables → Actions → Variables: las VITE_FIREBASE_* y VITE_API_BASE_URL.
  • En Firebase, ganevel.corvelsa.com en Authentication → Settings → Authorized domains (y localhost para desarrollo).

El flujo copia index.html como 404.html para que los enlaces profundos funcionen en Pages.

Reglas, índices y Storage

npx firebase-tools deploy --only firestore:indexes,firestore:rules,storage

.firebaserc fija el proyecto. Un índice nuevo tarda unos minutos en construirse; mientras tanto, las consultas que lo necesitan responden 503.

Versiones de Node alineadas

.nvmrc, la imagen del Dockerfile y el flujo de Pages deben usar Node 22 o superior. Con Node 20, pnpm install falla con ERR_UNKNOWN_BUILTIN_MODULE: node:sqlite.

Limitaciones y trabajo pendiente

  • Sin corrección manual de un escaneo. Un administrador puede anular, pero no corregir una cantidad mal leída.
  • Los productos obligatorios no bloquean hitos. Se muestran como pendientes, pero los hitos se alcanzan solo por puntos.
  • Paginación parcial. listUsers y listDocuments tienen tope fijo; necesitarán cursores con más volumen.
  • Sin vista del avance de un participante para el administrador.
  • Sin OCR alterno ni reintentos si Vision falla.
  • Sin entorno de pruebas separado: local y publicado comparten el proyecto de Firebase.
  • Requerimientos del documento del proyecto sin implementación: bloqueo tras 5 intentos, expiración de sesión a 30 minutos, carga por lotes, puntos de venta, exportación a PDF/Excel, bitácora de auditoría y extracción de NIT y serie.
