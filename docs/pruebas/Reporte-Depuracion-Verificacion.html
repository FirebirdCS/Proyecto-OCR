2. SCRUM-112 · Mensajes de error en inglés en el panel de administración

2.1 Ficha

ClaveSCRUM-112
ComponenteAPI (servidor Express), con efecto en el panel de administración
ClasificaciónDefecto. El error humano fue redactar los mensajes del servidor para programadores y en inglés; el defecto está en el código (15 archivos del servidor); el fallo es lo que ve el administrador: textos en inglés y un «Validation failed» que no dice qué corregir.
SeveridadMedia: no bloquea ninguna función ni altera datos, pero el administrador no entiende por qué se rechaza lo que hizo.
Prioridad (riesgo)Alta: impacto 2 (medio) × probabilidad 3 (alta) = 6 de 9. Cualquier dato inválido o acción no permitida lo muestra.
Atributo ISO/IEC 25010Usabilidad: capacidad de reconocimiento y protección frente a errores de usuario

RelacionadoCP-39 (anulación): con un motivo fuera de 3–300 caracteres, la API responde «Validation failed»

2.2 Pasos para reproducir

  1. Iniciar sesión como administrador.
  2. Campañas: crear una campaña en borrador sin productos ni hitos y elegir Activar.
  3. Productos: eliminar un producto que use una campaña en borrador o activa (por ejemplo, Paracetamol).
  4. Usuarios: crear una cuenta con un correo que ya está registrado.

2.3 Análisis de causa raíz

  • El cliente muestra el texto del servidor tal cual. client/src/services/api.ts crea el error con payload.error, y cada panel de administración hace setError(cause.message). Los textos en español de esos paneles solo aparecen cuando la respuesta no trae mensaje.
  • El servidor redactaba todos sus mensajes en inglés: los HttpError de 15 archivos y los mensajes de las reglas de campaña en types/campaigns.ts.
  • Los errores de validación (Zod) se respondían siempre como «Validation failed». El detalle iba en details, que la pantalla no muestra, así que el administrador no sabía qué campo corregir.
  • Por qué no se detectó antes: la pantalla del escáner (rol Usuario) no tiene el problema, porque traduce por código (duplicate_receipt, daily_limit…) con la tabla REFUSALS de UserDashboard.tsx. El panel de administración nunca recibió ese tratamiento. Además, los formularios bloquean la mayoría de los datos inválidos antes de enviarlos, así que el mensaje de validación casi nunca se veía.

2.4 Corrección aplicada

Se tradujeron los mensajes en el servidor, que es donde se originan. La otra opción era traducir en cada pantalla por código, pero la API solo tiene este cliente, que es en español: corregir en el servidor arregla todas las pantallas a la vez, incluidas las futuras. Los códigos de error para el escáner no cambian, así que su pantalla sigue funcionando igual.

3. SCRUM-116 · El sitio no fuerza el protocolo HTTPS

3.1 Ficha

ClaveSCRUM-116
ComponentePublicación del cliente web (GitHub Pages con el dominio propio ganevel.corvelsa.com)
ClasificaciónDefecto de configuración. El error humano fue no activar «Enforce HTTPS» al configurar el dominio propio; el defecto está en la configuración de GitHub Pages, no en el código; el fallo es que el sitio se sirve sin cifrar a quien entra por http://.
SeveridadAlta: afecta la confidencialidad y la integridad de la página donde el usuario escribe su contraseña.
Prioridad (riesgo)Alta: impacto 3 (alto) × probabilidad 2 (media) = 6 de 9. Solo ocurre al entrar por http:// (dirección escrita a mano o enlace viejo), pero entonces ocurre siempre.
Atributo ISO/IEC 25010Seguridad: confidencialidad e integridad
Ambiente donde se encontróSitio publicado ganevel.corvelsa.com (GitHub Pages), Edge en Windows 11 y curl, 13/10/2026
RelacionadoSCRUM-57 (requerimientos no funcionales), SCRUM-59, CP-44, RNF-03

3.2 Pasos para reproducir

  1. Escribir http://ganevel.corvelsa.com en la barra de direcciones, con http y sin la «s».
  2. Revisar la dirección final y el candado del navegador.
  3. Para comparar, abrir http://ocr-api-3bi5lk4hta-uc.a.run.app/api/health.
PasoResultado esperadoResultado obtenido
1 y 2Redirige a https://ganevel.corvelsa.com y muestra el candadoResponde HTTP/1.1 200 OK por http://, no redirige y el navegador marca «No seguro»
3Redirige a https://302 Found hacia https:// (correcto)
curl -I http://ganevel.corvelsa.com
HTTP/1.1 200 OK
Server: GitHub.com
Content-Type: text/html; charset=utf-8

3.3 Análisis de causa raíz

  • En el repositorio de GitHub, Settings → Pages → Enforce HTTPS no estaba activada. El certificado del dominio sí existía, porque https://ganevel.corvelsa.com respondía con candado, pero GitHub Pages no obligaba a usarlo.
  • La API no tenía el problema: Cloud Run redirige a HTTPS siempre, sin configuración.
  • Por qué no se detectó antes: todos los enlaces del equipo usan https://, y los navegadores recuerdan la versión segura de un sitio ya visitado, así que el fallo solo se ve al escribir http:// o al usar curl. Lo encontró la verificación de requerimientos no funcionales (SCRUM-57).
  • Impacto: una página servida sin cifrar puede ser leída o alterada por alguien en la misma red (por ejemplo, un Wi-Fi público) antes de que el usuario escriba su correo y su contraseña. El inicio de sesión de Firebase viaja cifrado, pero el código de la página que lo llama no.

3.4 Corrección aplicada

Se activó Enforce HTTPS en Settings → Pages del repositorio. No requiere cambios de código ni volver a publicar el sitio: GitHub empieza a responder 301 hacia https:// en todo el dominio.
